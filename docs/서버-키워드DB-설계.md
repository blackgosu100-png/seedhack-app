# 서버 키워드 DB 설계 (2026-11-16)

수강생 앱이 대표님 맥의 키워드 DB 파일 없이도 키워드 추천·키워드 분석을 쓰게 한다.
키워드 DB는 대시보드 서버(Supabase)에 두고, 앱은 필요한 답만 받아 간다.

## 1. 지금 앱이 키워드 DB를 쓰는 곳

| 쓰는 곳 | 하는 일 | 지금 읽는 것 |
|---|---|---|
| 키워드 추천 깔때기 | 864,950개 → 팔리는 것 → 누구나 → 안전 → AI 검수 → 예산 개수 | `sellar_YYYY-MM.db` 전체를 메모리로(`kw-combo.js load`) |
| 키워드 추천 받기 | 처음 보는 키워드 10개 뽑기(처음이에요 A·B·C / 팔아봤어요 L·M) | 위 결과 + `kw_judge_YYYY-MM.json` |
| 받은 기록·하루 횟수 | 10개 × 하루 10번 + 보너스 5번 | 앱 저장소 `recoDraw`(수강생이 지우면 초기화됨) |
| 키워드 분석 | 월검색량 + 서브키워드 15개 | `kwdb.js lookup` |
| 상품명 짓기 | 서브키워드 40개 + 조합 검색량 | `kwdb.js nameLookup` |
| 유명 브랜드 판별 | 브랜드 이름의 월검색 합 1만 이상 | `kw-combo.js famousBrands` |

## 2. 구조

```
씨드핵 앱 ──(앱 로그인 토큰 · 승인된 수강생)──▶ 대시보드 서버 /api/signal/kw/* ──▶ Supabase 표
                                                              ▲
대표님 맥: 월 1회 tools/kw-publish.mjs ── sellar DB + AI 검수 결과를 올림 ──┘
```

- 앱은 키워드 DB 원본을 받지 않는다. 한 번에 키워드 10개, 키워드 1개의 검색량처럼 **필요한 답만** 받는다.
- 인증·하루 한도는 이미 있는 `/api/signal/ai`와 같은 방식(앱 로그인 토큰 + `vendors.status='approved'`).
- 대표님 맥처럼 로컬 DB 파일이 있으면 지금처럼 로컬로도 돌 수 있게 둔다(개발·오프라인용).

## 3. 서버 표 4개

| 표 | 행 수(9월 기준) | 내용 |
|---|---|---|
| `kw_meta` | 달마다 1줄 | 달, 상태(올리는 중/사용 중), 깔때기 숫자(864,950 · 33,234 · 18,640), 올린 시각 |
| `kw_pool` | 약 18,640 | 추천 후보: 검색량·가격·1위 리뷰·로켓/해외 비율·계절·안전 필터 표시·AI 검수(ok/hold/no·이유·태그·설명) |
| `kw_all` | 864,950 | 키워드 분석·상품명·브랜드용: 키워드·카테고리·월검색·추세·평균가·리뷰·로켓·브랜드 여부·계절 |
| `kw_draws` | 받을 때마다 10줄 | 누가(vendor_id) 언제 어떤 키워드를 어떤 기준으로 받았는지 |

- 늘 "제외할 것"(브랜드·캐릭터·식품·화장품 등)과 안전 필터 표시는 **올릴 때 미리 계산**해서 `kw_pool`에 넣는다. 서버와 앱이 제외 사전을 따로 들고 있지 않게.
- `kw_all`은 37칸 중 앱이 쓰는 12칸만 올린다.
- 예상 용량: `kw_all` 약 130MB + 색인 약 100MB, 나머지는 수 MB. 합계 약 250MB.
- 달이 바뀌면 새 달을 다 올린 뒤 `kw_meta`에서 한 번에 바꾼다. 지난달은 한 달 뒤 지운다.
- `kw_draws`가 생기면 3번 과제(수강생끼리 같은 키워드 덜 겹치게)를 바로 붙일 수 있다.

## 4. 서버 주소(API)

| 주소 | 앱의 어디서 | 돌려주는 것 |
|---|---|---|
| `POST /api/signal/kw/scan` | 추천 시작 화면 깔때기 | 단계별 개수·빠진 이유(키워드 목록은 안 줌) |
| `POST /api/signal/kw/draw` | 🔍 AI 소싱 시작 | 처음 보는 키워드 10개 · 남은 횟수 (서버가 횟수 확인 후 `kw_draws`에 기록) |
| `GET /api/signal/kw/state` | 지난 결과 보기 | 남은 횟수 · 지난 묶음 30개 |
| `GET /api/signal/kw/lookup?kw=` | 키워드 분석 | 월검색 등 1줄 + 서브키워드 15개 |
| `POST /api/signal/kw/name` | 상품명 짓기 | 서브키워드 40개 + 조합 검색량 |
| `POST /api/signal/kw/brands` | 키워드 추천 카드 "틈" 계산 | 유명 브랜드 이름 목록 |

- 뽑기·깔때기 계산은 지금 앱의 코드(`kw-combo.js scan·draw`)를 그대로 옮긴다. 대시보드에 이미 앱 코드를 옮겨 둔 방식(`signal-detail-copy.mjs`)과 같게, 순수 계산 부분을 `src/shared/kw-core.js`로 떼어 양쪽이 같은 파일을 쓴다.
- 서버는 `kw_pool`(약 18,640줄, 3MB 안팎)을 달마다 한 번 읽어 메모리에 두고 계산한다.
- 서브키워드 찾기(`키워드 포함 검색`)는 Postgres 글자 조각 색인(pg_trgm)을 쓴다.
- 하루 한도: 키워드 받기 10번(+보너스 5번, 하루 1번)은 서버가 센다. 앱 저장소를 지워도 초기화되지 않는다. 키워드 분석·상품명 조회는 1인 하루 수백 번 정도로 넉넉하게 막아 둔다(원본을 통째로 긁어 가는 것 방지).

## 5. 매달 갱신 (대표님 맥에서 한 번)

1. keyword-pipeline으로 새 달 `sellar_YYYY-MM.db` 만들기 (지금과 같음)
2. AI 검수 `tools/kw-judge.mjs` 돌리기 (지금과 같음 · 검수 범위 넓히기는 2번 과제)
3. **새로** `node tools/kw-publish.mjs` — 표 4개에 새 달을 올리고, 개수를 맞춰 본 뒤 사용 중으로 바꿈
4. 수강생 앱은 다음 요청부터 새 달 데이터를 씀(앱 업데이트 필요 없음)

## 6. 앱에서 바뀌는 것

- `kw-combo.js`·`kwdb.js`: "서버에 묻기"를 기본으로. 로컬 DB 파일이 있고 설정에서 고르면 로컬로.
- 받은 기록·하루 횟수(`recoDraw`)는 서버 기록을 쓴다. 지금 대표님 맥의 기록 403개는 처음 연결할 때 서버로 한 번 옮긴다.
- 키워드 분석·상품명 조회 결과는 앱이 하루 동안 기억해 같은 키워드를 다시 묻지 않는다.
- 서버가 안 될 때: 키워드 추천은 "잠시 뒤 다시"를 보여 주고, 키워드 분석은 지금처럼 Wing 숫자만으로 보여 준다.

## 7. 작업 순서

| 단계 | 할 일 | 끝났다는 기준 |
|---|---|---|
| 1 | Supabase 표 4개 + 색인 만들기(SQL 파일) | 표가 생기고 빈 조회가 됨 |
| 2 | `tools/kw-publish.mjs` 만들고 9월 데이터 올리기 | 서버 개수 = 864,950 / 18,640 / AI 검수 1,206 |
| 3 | 서버 주소 6개 만들기 | 같은 조건에서 로컬과 서버의 깔때기 숫자가 같음 |
| 4 | 앱을 서버로 연결 + 로컬로 돌아가는 길 | 대표님 맥에서 DB 폴더를 잠시 치워도 추천·분석이 됨 |
| 5 | 수강생 계정으로 확인 후 앱 배포 | 수강생 PC에서 추천 10개가 나옴 |

## 8. 확인 안 된 것

- Supabase 요금제의 DB 용량 한도 (약 250MB가 더 들어감 · 무료 요금제는 전체 500MB)
- Vercel 함수 메모리·시간이 `kw_pool` 계산에 충분한지 (18,640줄이라 문제없을 것으로 봄 · 2단계에서 잼)
- 제휴 키워드 DB를 서버에 올려 수강생에게 결과로 보여 주는 것이 제휴 조건에 맞는지
